# سجل القرارات

**قاعدة السجل:** لا نمحو قرارًا قديمًا لتغيير الرأي. نضيف قرارًا لاحقًا يذكر ما استُبدل وسببه وأثره. هذه قرارات تحكم إعداد الخطة؛ المقترحات التنفيذية لا تعني موافقة على الإنتاج أو الميزانية.

## DEC-001 — تعديل توثيقي دون تغيير النظام

- **التاريخ:** 2026-10-27.
- **الحالة:** معتمد لنطاق هذه الجلسة استجابة لطلب خطة.
- **القرار:** لا تعديل لـsrc/public/scripts/SQL أو الاعتماديات أو manifests الإصدار أو إعدادات التشغيل وworkflows. تضاف خطة وعقود وسياق استئناف وروابط وقالب PR فقط.
- **السبب:** طلب المستخدم خطة كاملة مع عدم التعارض، لا تنفيذ هجرة شاملة أو نشر.
- **الأثر:** الإصدار يبقى 0.2.0؛ لا تُعرض الميزات المخططة كأنها موجودة. تنفيذ أي مهمة لاحقًا يحتاج نطاقًا واختبارات وموافقة مناسبة.

## DEC-002 — فصل ذاكرة المشروع عن ذاكرة التطبيق

- **التاريخ:** 2026-10-27.
- **الحالة:** معتمد للتخطيط؛ تخزين التطبيق لم يُنفذ.
- **القرار:** Git/AGENTS/handoff للمتطلبات والقرارات والعمل؛ MySQL وسياسة خصوصية لمحادثات المستخدم والمهام في مرحلة DATA.
- **السبب:** المحادثة والـDOM وsessionStorage وذاكرة العرض لا توفر حفظًا دائمًا ولا يمكنها ضمان الاستئناف.
- **الأثر:** لا يُخزن محتوى العملاء أو مفاتيحهم في وثائق الاستمرارية. نقل التطبيق إلى حفظ دائم يحتاج موافقة وتصميمًا وترحيلًا واختبار restart وتفرد وملكية.

## DEC-003 — مصدر واحد للحالة، مع حفظ التاريخ

- **التاريخ:** 2026-10-27.
- **الحالة:** معتمد لعملية العمل.
- **القرار:** STATE للتركيز والواقع؛ BACKLOG لحالات المهام؛ DECISIONS للأسباب؛ الخطة للنطاق؛ runbooks للأوامر المنفذة؛ Git وGitHub للفرع/PR/CI الحيين.
- **السبب:** تقارير 0.1.0 و25/27 أكتوبر وأسماء الفروع القديمة تحتوي أرقامًا انتهت صلاحيتها. PR #17 مدموج الآن عند 6f1dbb3؛ تقرير سابق قال إنه مفتوح.
- **الأثر:** نحافظ على النص التاريخي ونضيف تنبيهًا، ولا نتبع اسم فرع/حالة قديمة بدل ما تعطيه البيئة وGit الحاليان. أي نسخة سحابية لاحقة لقطة بتاريخ ومرجع فقط.

## DEC-004 — التوافق بوابة وليس وعدًا مطلقًا

- **التاريخ:** 2026-10-27.
- **الحالة:** معتمد كقاعدة أمان للتخطيط؛ الفحوص الإضافية مستقبلية.
- **القرار:** جرد منقح، عقود N/N−1، restore حقيقي وترحيل expand/backfill/switch/contract مع فصل الترحيل عن rollback.
- **السبب:** بيئة المستخدم غير معروفة وبوابة schema الحالية تمنع اختلاف الأرقام حتى لو كان SQL إضافيًا.
- **الأثر:** يلزم تصميم إصدار جسر/بوابة ترحيل، ولا نرفع maxReadable لتجاوز المنع بلا اختبار. البيانات والتكلفة والنشر تحتاج موافقة مستقلة.

## DEC-005 — حداثة 2026 مشروطة بالتوافق والدليل

- **التاريخ:** 2026-10-27.
- **الحالة:** اتجاه مقترح للتنفيذ بعد الفحص.
- **القرار:** إبقاء Node 24 المختبر، وتقييم Node 26 بعد بدء LTS المجدول في 2026-10-28 والتحقق منه؛ إبقاء 22 خلال نافذة دعمه. تقييم MCP 2026-07-28 بمحولي legacy/modern واختبارات، وليس تغيير ثابت التاريخ.
- **السبب:** جدول Node الرسمي ووسم MCP المنشور يثبتان تغييرات مهمة؛ MCP الحديث stateless ويزيل handshake القديم. الانتقال الأعمى يكسر عملاء موجودين.
- **الأثر:** ذاكرة التطبيق بمعرفات مستقلة عن اتصال MCP. لا إعلان مطابقة أو LTS قبل التحقق الفعلي. مراجع مثبتة في خطة 2026.

## DEC-006 — تطوير تدريجي لا بنية موزعة تلقائيًا

- **التاريخ:** 2026-10-27.
- **الحالة:** اتجاه تخطيط؛ فصل خدمات/شراء بنية بانتظار اعتماد الحاجة.
- **القرار:** الحفاظ على Express/ESM/MySQL والأصول المحلية. إضافة حدود وحدات وoutbox أولًا، وفصل عامل/replicas عند الحاجة؛ لا إلزام بـRedis أو vectors أو Kubernetes.
- **السبب:** زيادة الخدمات تزيد كلفة التعارض والاستعادة. عزل القواطع الحالي داخل عملية واحدة ليس HA، لكن هذا لا يبرر إعادة كتابة بلا قياس.
- **الأثر:** لكل مكوّن جديد سبب وحدود وصلاحيات وتكلفة ودليل تعافٍ. لا ضمانات توافر من طبقة مجانية نائمة.

## DEC-007 — لا إعادة أفعال خارجية لاستعادة سياق

- **التاريخ:** 2026-10-27.
- **الحالة:** قاعدة أمان قائمة ومستقبلية.
- **القرار:** حفظ تقدم/نية العملية، والتعامل مع outcomeUnknown بالمصالحة أو المراجعة؛ لا إعادة إرسال/موعد بسبب restart أو checkpoint أو إعادة طلب نقل.
- **السبب:** قد تنجح الكتابة عند المزوّد قبل ضياع الرد. معرف JSON-RPC أو outbox وحده لا يثبت exactly-once عالميًا.
- **الأثر:** DATA-003 قبل استئناف أفعال؛ تستمر الموافقات والتحقق الخادمي، ولا يُعتمد على النموذج كحد صلاحية.

## DEC-008 — تنفيذ فعلي مجاني دون اختلاق نشر أو تجاوز بطاقة

- **التاريخ:** 2026-10-27.
- **الحالة:** طلب تنفيذ جديد؛ يستكمل DEC-001 التخطيطي ولا يمحو تاريخه.
- **القرار:** اختيار Render Free لخدمة واحدة + Aiven Free MySQL + نطاق فرعي HTTPS، وبدء التنفيذ/الفحص/الدفع. تسجيل دخول الحسابات وتفويضها يبقيان لدى المالك؛ لا مفاتيح في الدردشة أو Git ولا خطط مدفوعة أو بطاقة/تجاوز تحقق.
- **البدائل:** Pages واجهة ثابتة فقط ومحاولة تفعيله403؛ HF compute الجديد مدفوع فلا يُقدّم كحل مجاني. لا استخدام Actions كخادم دائم ولا keep-alive لتجاوز نوم الطبقة المجانية.
- **الأثر:** HOST-001/HOST-002 تنفيذ وفحص؛ HOST-003 يحتاج دليل خدمة عامة في حساب المالك. CI/preview/Blueprint لا يغلقه. جرد COMP-001 جزئي؛ لا لمس إنتاج أو افتراض حذف بيانات مجهولة.

## DEC-009 — تجميع اختياري لا تغيير افتراضي أو migration صامت

- **التاريخ:** 2026-10-27.
- **الحالة:** متحقق في0.2.1/CI9010120؛ إنتاج الحسابات الخارجية غير منشور.
- **القرار:** إعادة استخدام routers الأصلية على منفذ MCP بخيار معطل افتراضيًا، TLS/CA موثقة، وempty-only صريح لأول قاعدة خالية حتى من views. PORT الاستضافة يطبق في الوضع الموحد فقط كي لا يكسر فصل المنافذ القديم. schema1 و12أداة بلا تغيير.
- **السبب:** طبقة مجانية واحدة، دون مضاعفة الخدمات أو إعادة كتابة حماية OAuth/WhatsApp. لا نستغل الحاجة للنشر لإدخال ترحيل أو فقد بيانات.
- **الأثر:** bootstrap يرفض قاعدة غير متوافقة دون repair؛ الأعمدة ليست تدقيق فهارس كاملًا. الاختبار المصطنع يستعيد dump ويقرأه MCP0.2.0، لا يثبت restore حساب المالك أو كل أسطح N/N−1. 0.2.0 لا يعرف تجميع REST؛ لا وعد برجوع كامل للنظام منه. `allCapabilitiesVerified=false` يبقى حتى وجود مسار قبول خارجي، ولا يُستنتج من إعداد أو اسم نطاق.

## DEC-010 — توظيف أسرار المستودع التسعة على الخادم وعقد التوافق الإضافي لـMCP

- **التاريخ:** 2026-10-27.
- **الحالة:** متحقق محليًا على 0.2.1/schema1 (75/75 اختبار وحدة + فحص عدم التسريب)؛ قيد التحقق الحي في CI الفرع.
- **القرار:**
  1. ربط أسرار المستودع التسعة (`AGENETROUTERAPI_KEY`، `AI_GATEWAY_API_KEY`، `CELIA_MCP_API_TOKEN`، `CELIA_VOICE_ID`، `DEEPSEEK_API_KEY`، `ELEVENLABS_API_KEY`، `FIGMA_ACCESS_TOKEN`، `GEMINI_API_KEY`، `YOUR_CODATA_API_KEY`) على الخادم فقط عبر `src/ai-providers.js` و`src/secrets-hub.js` خلف مصادقة `Bearer` للمالك وقواطع دوائر مستقلة وحارس HTTPS مضاد لـSSRF، مع تصفيرها بالكامل في sandbox الواجهة العامة (`/ui/workspace/rpc`) والنسخة الثابتة.
  2. في وضع `auto` للذكاء الاصطناعي يستدعي النظام مزودًا سحابيًا واحدًا على الأكثر افتراضيًا قبل التحول للمحلي (`CELIA_AI_ALLOW_CLOUD_FAILOVER=false`) منعًا لمشاركة نصوص العملاء عبر شركات متعددة دون تفويض صريح (AI-002 / SEC-002 / SEC-003).
  3. إبقاء ربط `FIGMA_ACCESS_TOKEN` و`YOUR_CODATA_API_KEY` للقراءة والفحص فقط (`primaryTransactionalStore: false` و`automaticMigrationAllowed: false` استمرارًا لـDEC-002 وDEC-009)، وحماية توليد الصوت عبر ElevenLabs بمفتاح `Idempotency-Key` استمرارًا لـDEC-007.
  4. اعتماد فاحص التوافق الدلالي غير الكاسر (`src/mcp-contract.js` — `assertBackwardCompatibleMcpTools`) بدل المطابقة النصية الجامدة لمخطط `MCP_TOOLS` مع إبقاء الـ12 أداة الافتراضية ثابتة وجعل الأدوات الـ4 الإضافية اختيارية (`CELIA_EXTENDED_MCP_TOOLS=true`)، لإصلاح تعارض توافق 0.2.0 مع الحقول الاختيارية الإضافية مثل `idempotencyKey` (COMP-002).
- **السبب:** تلبية طلب المالك بتوظيف الأسرار التسعة في النظام بالكامل دون كشف أي سر في المتصفح أو السجلات أو كسر عملاء 0.2.0 أو التوسع في صلاحيات كتابة غير معتمدة.
- **الأثر:** جاهزية موحدة ومنقحة عبر `/api/secrets/status` و`celia://secrets/readiness` وبوابة `npm run check:secrets` في CI؛ تبقى أسرار GitHub Actions محصورة في مهام GitHub، ويلزم إدخال ما يرغب به المالك في مخزن Render عند النشر العام (HOST-003).

## DEC-011 — بناء Celia Google Spider v0.1.0 كحزمة Python داخل المستودع

- **التاريخ:** 2026-10-27.
- **الحالة:** متحقق محليًا (اختبارات 10/10 عبر unittest وpytest + مصافحة MCP stdio)؛ قيد التحقق في CI الفرع. مزامنة حية مع Google Drive لم تُجرَ لعدم وجود `credentials.json` في بيئة الجلسة (SPDR-002).
- **القرار:**
  1. بناء الحزمة في مسار علوي داخل المستودع `celia-google-spider/` (حزمة Python مستقلة بـ`pyproject.toml` و`tests/` و`README.md` عربي و`LICENSE` MIT وأرشيف ZIP في `dist/` المتجاهل)، دون إنشاء مستودع GitHub جديد أو أي دفع خارج الفرع المخصص للجلسة.
  2. قيود صريحة: OAuth بنطاق `drive.readonly` فقط، خادم MCP عبر stdio بلا أي منفذ، فهرس محلي في `~/.celia_spider/knowledge.sqlite3` (يُعاد تحديده عبر `CELIA_SPIDER_DATA_DIR`)، بحث معجمي فقط بلا embeddings، المزامنة إدراج/تحديث فقط ولا تحذف أي عنصر محلي غائب عن Drive، حد افتراضي 2000 ملف، أول ورقة في Google Sheet فقط، والاتصال بـChatGPT خارج النطاق (يتطلب موصلاً بعيداً/خطة مدفوعة).
  3. ملفا `credentials.json` و`token.json` ممنوعان من Git عبر `.gitignore` على مستوى الحزمة؛ لا تُوضع أي قيمة سرية (بما فيها أسرار المستودع التسعة) في ملفات الحزمة أو السجلات.
  4. توافق خادم MCP مع مخططتَي SDK (v2 `MCPServer` مع ارتداد إلى v1 `FastMCP` عند غيابه)، واختبار مصافحة stdio حقيقي يتأكد من الأدوات الست بالضبط.
- **السبب:** طلب المستخدم ببناء «Celia Google Spider v0.1.0» من المواصفة الواردة في رسالته بعد التحقق من انعدام أي أثر سابق له محليًا وعلى GitHub؛ مكانة المستودع والفرع تُحدَّد ببيئة الجلسة، والوضوح يغني عن استئناف أسئلة التوضيح التي تخطّيها المستخدم.
- **الأثر:** 17 ملف مصدرًا في `celia-google-spider/` + وظيفة CI اختيارية لاختبارات Python؛ لا يمس كود Node أو schema أو الإصدار 0.2.1 أو أسرار المستودع، ولا يُعلن نشرًا أو مزامنة حية قبل قبول المالك.

## DEC-012 — الاتجاه المنتجي: وكيل متكامل على نمط Manus، بالترتيب المعلن

- **التاريخ:** 2026-10-27.
- **الحالة:** مخطط — اتجاه فقط؛ لا قدرة منفذة ولا ادعاء تشغيل.
- **القرار:** اعتماد هدف «نظام متكامل مثل Manus» على أنه الهدف المنتجي للنظام بعد 0.2.1، على أربع مراحل
  AGENT-001..AGENT-004 موثقة في [خطة الوكيل](../agent-runtime-plan.md)، مع أربع قواعد غير قابلة للتفاوض:
  (1) لا إعادة تنفيذ عمياء لأثر خارجي و`outcomeUnknown` يحتاج مصالحة؛ (2) تصنيف مخاطر إلزامي لكل أداة وموافقة
  صريحة لأي أثر خارجي أو غير قابل للتراجع؛ (3) لا تشغيل كود مولّد من نموذج قبل عزل حاوية بلا وصول للمضيف؛
  (4) تسجيل التكلفة/التوكنات في كل تشغيل وإيقاف عند تجاوز الميزانية.
- **السبب:** طلب المالك الصريح أن الغرض من النظام هو أن يكون متكاملًا على نمط Manus؛ القرار يثبّت المعنى
  القابل للاختبار (حلقة، ذاكرة مهمة، مخرجات، عزل، أثر خارجي بموافقة، شفافية، عزل مستخدمين) بدل إطلاق الوصف
  كتسمية تسويقية.
- **البدائل المرفوضة:** (أ) تسمية النظام الحالي «وكيلًا» دون حلقة ولا ذاكرة مهمة — ادعاء غير صحيح؛ (ب) البدء
  بالعزل وتشغيل الكود أولًا (M3) قبل وجود ذاكرة تشغيل وموافقات — مخاطرة أثر خارجي بلا تدقيق؛ (ج) بناء منتج
  متعدد المستخدمين قبل إثبات الحلقة على المالك — تكلفة ومخاطر خصوصية بلا دليل قيمة.
- **الأثر:** لا تغيير على `0.2.1`/`schema 1` ولا على الأسرار أو النشر بهذا القرار؛ `schema 2` لا يُكتب إلا عبر
  مسار COMP-003 (migration ledger)؛ AGENT-003 وAGENT-004 يبقيان بانتظار قرار ميزانية/مستخدمين من المالك.
  الافتراض الافتراضي عند غياب القرار: موافقة لكل أثر خارجي، Google Workspace أولًا، طبقة مجانية حتى M2، مالك
  واحد مع تحقق ملكية على كل صف. **لا يجوز لأي وثيقة أن تصف النظام بأنه «مثل Manus» قبل إنجاز AGENT-001.**

## DEC-013 — حلقة وكيل M1 بمخزن صريح (MySQL أو SQLite) وسجل ترحيل، بلا ذاكرة ولا ادعاء Manus

- **التاريخ:** 2026-10-27.
- **الحالة:** منفذ ومختبر محليًا على SQLite (25 اختبارًا ضمن 124)؛ **غير** متحقق على MySQL حي، ولا نشر،
  ولا يشغّل نموذجًا لغويًا. AGENT-001 يبقى `جارٍ`؛ COMP-003 يبقى `جارٍ`.
- **القرار:**
  1. بناء حلقة M1 (`src/agent/*`) كمكوّن اختياري معطّل افتراضيًا (`CELIA_AGENT_RUNTIME=off`) بمخزنَين صريحين فقط:
     MySQL (إنتاج، جداول ينشئها `npm run migrate -- --apply` وحده) أو SQLite دائم محلي/تجريبي مرفوض في الإنتاج.
     **لا وضع ذاكرة** ولا ارتداد صامت؛ تعذّر المخزن يعيد `503` ويُبقي بقية النظام عاملًا.
  2. إدخال سجل ترحيل `schema_migrations` ببصمات SHA-256 ورفض drift وdry-run افتراضي، وتطبيق الجداول الإضافية
     `agent_*` عبره. الجداول الخمسة الأساسية و`database.schema = 1` لا تتغير.
  3. تقييد M1 بأدوات `read`/`internal_write`: كل أثر خارجي أو غير قابل للتراجع يُرفض بحالة `waiting_approval`
     حتى تنفيذ AGENT-002 (outbox وموافقات) وAGENT-003 (عزل). أي استدعاء غير محسوم بعد انقطاع يصبح `unknown`
     ويوقف التشغيل للمصالحة، لا يُعاد تلقائيًا.
  4. المخطط الحالي حتمي ومعلن كذلك؛ لا يجوز تسمية النظام وكيلًا عامًا أو «مثل Manus» حتى ربط نموذج ومزوّد
     واختبار جودة (AI-002) ثم AGENT-002.
- **السبب:** طلب المالك التنفيذ لا الإرشاد، وأعلى قيمة قابلة للإثبات بلا بطاقة أو حساب خارجي هي طبقة الحالة
  والحلقة والاستئناف وبوابة المخاطر؛ وهي أيضًا شرط AGENT-002/003/004.
- **البدائل المرفوضة:** (أ) مخزن مؤقت في الذاكرة «للتجربة» — يخلق ادعاء استئناف كاذبًا؛ (ب) إنشاء جداول عند
  startup — يخالف قاعدة عدم الترحيل التلقائي؛ (ج) تشغيل أدوات الكتابة أو التقويم الآن — يخالف DEC-007/DEC-012.
- **الأثر:** لا تغيير في الإصدار `0.2.1` أو manifest أو 12 أداة MCP أو مسارات Google/WhatsApp؛ المسارات الجديدة
  `/api/agent/*` اختيارية وخلف مصادقة المالك. الرجوع إلى صورة لا تعرفها يترك جداول إضافية بلا استخدام. يلزم
  قبل الإنتاج: تطبيق الترحيل في MySQL حي، اختبار CI، واستئناف تلقائي بقرار صريح.

## DEC-014 — حوكمة الوكيل: عقد هدف، بوابة موافقات قابلة للاستئناف، سجل أدلة مسلسل، ومُتحقِّق مستقل

- **التاريخ:** 2026-10-27.
- **الحالة:** منفذ ومختبر محليًا على SQLite (31 اختبارًا جديدًا، الإجمالي 185)؛ ترحيل MySQL `0003_agent-governance.sql`
  إضافي وجاهز عبر سجل الترحيل لكنه غير مطبَّق على قاعدة حية في هذه البيئة (لا MySQL محليًا؛ التغطية الحية في CI).
  AGENT-001 وAGENT-002 يبقيان `جارٍ`؛ لا ادعاء إتمام الموصلات الخارجية.
- **القرار:**
  1. **عقد الهدف بيانات لا نصًا** (`src/agent/goal-contract.js`): كل تشغيل يحمل `objective` و`success_criteria`
     و`constraints` و`stop_conditions` و`deadline` و`budget`، يُبنى حتميًا من حدود التشغيل الفعلية ويُحفظ في
     `agent_goal_contracts` ويُعرض في `/agent`، ويتحقق المُتحقِّق من بنيته آليًا.
  2. **بوابة موافقات كاملة** (`agent_approvals` + `POST /api/agent/runs/:id/approval`): التشغيل المتوقف
     `waiting_approval` صار له قرار مسجل (`approved`/`rejected`) بمفتاح idempotency وممثل وملاحظة، ثم استئناف
     محكوم. **قاعدة صارمة:** الموافقة تُرفض برمز `reconciliation_required` إن وُجد استدعاء حالته `unknown`
     أو `started`؛ المصالحة قبل أي استئناف، ولا إعادة تنفيذ عمياء أبدًا. الرفض يلغي التشغيل بلا أي أثر.
  3. **سجل أدلة إضافي فقط بسلسلة بصمات** (`src/agent/evidence.js` + جدول `agent_evidence`): كل مدخل
     `prev_hash`/`hash` من SHA-256 على ترتيب ثابت للحقول، وجذر `genesis` لكل تشغيل؛ أي كشف أو حذف يكسر السلسلة
     ويُرصد بالرقم والسبب. الاستدعاء الذي ماتت عمليته قبل كتابة دليله يُعاد بناؤه كمدخل `tool_call_reconciled`
     صادق يشهد على الصف الدائم لا على مشاهدة مزعومة.
  4. **مُتحقِّق مستقل** (`src/agent/verifier.js`) منفصل عن المنتِج، بلا كتابة وبلا تنفيذ غير قراءة، أحكامه
     ثلاثة حصرًا: `PASS`/`BLOCK`/`UNKNOWN`. يفحص سلامة السلسلة، اكتمال الأدلة، الحالات غير المحسومة، الموافقة
     على الأثر الخارجي، إعادة تنفيذ القراءات الحتمية المُعلَّمة صراحةً، مطابقة المخطط وترخيص/ثقة نتائج KB،
     ومعايير العقد الآلية. **لا تسليم بلا خطوة `verify`**؛ الحكم `BLOCK` يفشل التشغيل و`UNKNOWN` يرسله للمصالحة.
  5. يبقى منفذ الأثر الخارجي (outbox AGENT-002) والعزل (AGENT-003) غير مبنيين: الموافقة المسجلة بلا منفذ تنفيذ
     تُنهي التشغيل بخطأ صريح `external_connector_unavailable` بدل نجاح وهمي، والمخطط التجريبي يسلّم نتيجة محدودة
     تسمي الحد صراحةً.
- **السبب:** تحليل الفجوات أثبت أن `waiting_approval` كان طريقًا مسدودًا بلا قرار، وأن النجاح كان بلاغ الوكيل
  عن نفسه؛ أعلى قيمة قابلة للإثبات الآن هي إغلاق البوابة وجعل «ماذا حدث» قابلاً لإعادة البناء والتدقيق دون توسيع
  سطح الأثر الخارجي قبل وجود العزل والموصلات.
- **البدائل المرفوضة:** (أ) تنفيذ الأداة الخارجية فور الموافقة — يقفز over AGENT-002/outbox ويخالف DEC-007؛
  (ب) إضافة أعمدة إلى `agent_runs` بعملية ALTER — كسر لقاعدة الإضافة فقط وصعوبة idempotency في MySQL، عُوّضت
  بثلاثة جداول مستقلة؛ (ج) جعل المُتحقِّق جزءًا من الحلقة يكتب حالته بنفسه — يلغي استقلالية الحكم؛ (د) حجب
  نتيجة `UNKNOWN` وتحويلها نجاحًا — يخالف مبدأ التصريح الصريح بحدود ما يمكن التحقق منه.
- **الأثر:** ترحيل إضافي `0003` بثلاثة جداول و8 جداول `agent_*`، لا تغيير على الجداول الخمسة الأساسية أو
  `database.schema = 1` أو الإصدار `0.2.1` أو أدوات MCP. مساران جديدان مالك-فقط خلف Bearer القائم، وواجهة
  `/agent` تعرض العقد والموافقات والأدلة والحكم. الرجوع لصورة قديمة يترك الجداول الإضافية بلا استخدام بلا كسر.
