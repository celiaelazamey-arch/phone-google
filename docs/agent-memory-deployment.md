**الفرع:** `arena/820dcd1a-phone-google` · **خط الأساس:** `main@922ed4e` مع تعديلات WP-2.3 في الـworktree.

> هذه الوثيقة تصف ما يجب فعله **عند وجود تفويض مستقل لكل مرحلة**. لم يُنفَّذ في هذه المراجعة commit أو push أو PR أو نشر أو ترحيل على قاعدة خارجية. نجاح الفحوص المحلية لا يثبت نجاح staging أو الإنتاج.

## 3. المرحلة الأولى — التثبيت المحلي واستعداد PR

### 3.1 بوابة لا تُتجاوز قبل أي commit

تُعاد هذه الأوامر على النسخة التي سيُبنى منها الـcommit، وتُحفظ الأرقام دون أسرار:

```sh
git branch --show-current
git status --short
git diff --check
npm run check
npm run release:check
npm run now:check
npm run check:continuity
npm run check:secrets
node --test test/agent-memory.test.js test/agent-memory-routes.test.js
GITHUB_ACTIONS=true npm run -s test:coverage:ci
npm run build:pages
```

ثم تراجع `git diff --stat` و`git diff` و`git status --short`. **لا يُستخدم `git add .` آليًا قبل هذه المراجعة**: قد يلتقط ملفات غير مرتبطة أو أثرًا لا ينبغي دخول Git. تُضاف مسارات الحزمة صراحةً، ويُراجع `git diff --cached` قبل الـcommit. لا تُضاف `.env` أو رموز أو dumps أو تقارير تحوي بيانات مالك.

### 3.2 commit المحلي — مستقبلي ولم يُنفّذ هنا

بعد اقتصار المنطقة المؤقتة على الحزمة ومراجعة محتواها، يكون القالب المقترح:

```sh
git commit -m "feat(agent-memory): implement WP-2.3 / AGENT-009 deterministic memory architecture (DEC-053)"
```

وجود هذا القالب لا يعني أن commit أُنشئ. يُسجّل SHA الفعلي بعد إنشائه، ولا يُنسب إلى `922ed4e` الذي هو خط الأساس فقط.

### 3.3 push وPR — يتطلبان كلمة مالك صريحة

عند السماح بالدفع، يكون الفرع الوحيد المسموح:

```sh
git push origin arena/820dcd1a-phone-google
```

ثم يُفتح PR من هذا الفرع إلى `main` عبر `gh`، بجسم يتضمن:

- نطاق WP-2.3 والملفات و`DEC-053`، وعدم تغيير `schema=1` أو الإصدار.
- نتيجة **607/607** والتغطية الثلاثية وأسماء البوابات الناجحة.
- بوضوح: Playwright لم يبدأ محليًا لغياب Chromium، وقبول MySQL الجديد لم يُشغّل محليًا.
- طلب تشغيل CI على commit الـPR، بما فيه MySQL 8.4 وPlaywright، قبل أي دمج.

لا يُدّعى أن Branch protection يفرض هذه البوابات؛ حالة الحماية موثقة في `SEC-006`. الدفع أو فتح PR أو الدمج لا يحدث من هذه الوثيقة تلقائيًا.

## 4. المرحلة الثانية — قبل الترحيل وعلى staging

### 4.1 شروط البيئة والبيانات

- بيئة MySQL معزولة (يفضل MySQL 8.4 المطابق لاختبار التكامل)، لا قاعدة إنتاج ولا قاعدة مالك مجهولة.
- بيانات اصطناعية أو نسخة منقحة، ونسخة احتياطية مستقلة مع **restore مثبت** قبل أي تغيير إنتاجي.
- معرفة إصدار القاعدة والجداول والقيود الحالية، وعدم وجود drift في ملفات `schema_migrations`.
- أسرار الاتصال في مخزن أسرار المشغّل فقط؛ لا قيم في Git أو سجل الجلسة أو تقرير CI العام.
- تعيين هدف النشر ومالك القرار ونافذة التغيير وخطة الرجوع قبل `--apply`.

### 4.2 dry-run والقبول المعزول

```sh
npm run migrate                 # dry-run: لا يكتب
npm run migrate -- --status     # قراءة حالة السجل
npm run test:mysql              # فقط خدمة MySQL المعزولة التي يقبلها الحارس
```

`npm run test:mysql` ليس أمر قبول على خادم بعيد أو إنتاج؛ لا تُغيّر إعداداته لتجاوز حارس العزل. يُراجع أن الترحيلات المتوقعة هي `0002`–`0005`، وأن `0005` يحوي الجدولين والأعمدة `owner_id` و`source_run_id` و`created_at` و`expires_at` والقيود والفهارس.

### 4.3 apply على staging فقط بعد التفويض

```sh
npm run migrate -- --apply
npm run migrate -- --status
npm run migrate -- --apply       # قبول idempotency: لا pending جديد
npm run migrate -- --status
```

القبول المطلوب:

- `schema_migrations` يسجل `0005_agent-memory.sql` مرة واحدة، ولا يوجد drift.
- الجدولان `agent_thread_summaries` و`agent_owner_facts` موجودان، وعدد جداول `agent_` بعد كل الترحيلات هو **11**.
- القيود الفريدة: ملخص واحد لكل `thread_id`، وحقيقة واحدة لكل `(owner_id, tag)`؛ والفهارس والمراجع الأجنبية كما في الملف.
- تشغيل الذاكرة والحذف وقراءة المالك الآخر في `integration/mysql.integration.mjs` ينجح على InnoDB.

**تنبؤ الفشل الذي يجب توثيقه لا إخفاؤه:** إذا نجح إنشاء الجدول الأول وفشل الثاني، قد يبقى الأول موجودًا بلا قيد ناجح للملف في السجل. لا تُحذف الجداول ولا تُعلن rollback. تُفحص الحالة، يُصلح السبب، ثم يعاد `apply`؛ `IF NOT EXISTS` يسمح بإكمال الملف، لكنه لا يثبت صحة تعريف جدول قديم موجود مسبقًا، لذلك يلزم فحص التعريف الفعلي أيضًا.

## 5. المرحلة الثالثة — النشر والمزامنة

لا يبدأ النشر إلا بعد PR مدمج رسميًا وCI أخضر على الـcommit المستهدف وقبول staging المطلوب. يُسجّل قبل النشر: commit SHA، ونسخة الحزمة، واسم البيئة، ومالك الموافقة، ومعرف النشر، وحالة الترحيل.

الترتيب الآمن للقدرات:

1. تطبيق `0005` على الهدف المعتمد مع بقاء الكود السابق، ثم قراءة `--status` وفحص الجدولين.
2. نشر كود Express الجديد أو تفعيله، مع `CELIA_AGENT_RUNTIME=mysql` فقط بعد نجاح الترحيل. لا يوجد ترحيل تلقائي عند startup.
3. فحص `/readyz` و`/version` و`/api/agent/status` قبل فتح اختبارات الذاكرة.
4. تثبيت أدلة النشر والـcommit والـschema، ثم تشغيل قبول ما بعد النشر.

إذا كان الوضع السابق `off`، فتفعيل `CELIA_AGENT_RUNTIME=mysql` **تغيير تشغيلي مستقل** وليس نتيجة تلقائية للترحيل. أما Pages فتنشر الأصول الثابتة فقط، ولا تنشئ MySQL أو مسار الذاكرة. لا تُستخدم D1 أو PostgreSQL كبديل صامت.

لا يُوصف هذا الترتيب بأنه نشر بلا انقطاع؛ اختبار الانقطاع والرجوع يتبع [دليل الإصدارات والاستعادة](releases-and-recovery.md)، وهو بوابة مستقلة عن هذا التوثيق.

## 6. المرحلة الرابعة — قبول ما بعد النشر

تُستخدم بيانات اصطناعية ومالك اختبار. لا تُحذف ذاكرة مالك حقيقي، ولا تُطبع قيم الملخصات/الحقائق أو Bearer في السجلات؛ تُحفظ رموز الحالة والحقول البنيوية والأدلة المنقحة فقط.

### 6.1 الجاهزية وAPI

- [ ] `GET /readyz` يعيد الجاهزية المتوقعة مع تخزين MySQL الدائم، و`GET /version` يطابق الـcommit المنشور.
- [ ] `GET /api/agent/status` برمز المالك يبين `enabled:true` و`dialect:mysql`؛ الرمز غير الصحيح يفشل كما هو متوقع.
- [ ] `GET /api/agent/memory` يعيد `{summaries, facts}` للمالك، ولا يعرض الصفوف المنتهية افتراضيًا. لا يُفترض عدد ثابت من الحقائق.
- [ ] بعد تشغيل اصطناعي ينتهي بـ`run.finished`، يظهر ملخص الخيط والحقائق المشتقة من الخطوات الفعلية مع `source_run_id` الصحيح؛ نص مشتبه بسر لا يُحفظ.
- [ ] قراءة عنصر بمعرف مالك آخر تعيد **404**، ولا تكشف وجوده.
- [ ] `DELETE /api/agent/memory` لعنصر اصطناعي يعيد `deleted:true`؛ القراءة التالية تعيد **404**، وتفصيل التشغيل المصدر يحوي `memory_deleted` وسلسلة `evidenceChain.ok=true` دون النص المحذوف.
- [ ] فحص انتهاء صلاحية منفصل يثبت الإخفاء الافتراضي، وأن القراءة الصريحة بـ`includeExpired=true` مقصودة وموثقة.

### 6.2 الواجهة والمتصفح

- [ ] `/agent` يعرض «ما يتذكره الوكيل» بعد الاتصال وبعد `run.finished` من بيانات الخادم، بلا نسخة بديلة في المتصفح.
- [ ] الملخص والحقائق الفعلية ومصدرها ظاهرة؛ زر «حذف نهائي» يحذف ثم يعيد القراءة، ويظهر إثبات الحذف في التفاصيل.
- [ ] تمر حالة WP-2.3 في `e2e/agent.spec.js` على Chromium، مع 320px ولوحة المفاتيح وaxe وعدم وجود تمرير أفقي.
- [ ] تُرفع نتيجة Playwright من CI مع الـcommit؛ لا تُستبدل بنتيجة `build:pages`.

### 6.3 أوامر القبول في البيئة المناسبة

```sh
# على CI/الجهاز المزود بـChromium فقط
npm run test:browser -- e2e/agent.spec.js --grep 'WP-2.3'

# على خدمة MySQL المعزولة فقط، وليس على الإنتاج
npm run test:mysql

# على الرابط العام المعتمد بعد إدخال الرمز في بيئة المشغّل، لا في الأمر أو Git
npm run verify:live -- --url https://<approved-host> --expect-commit <full-commit-sha>
```

`verify:live` لا يثبت وحده كل اختبارات الذاكرة أو restore أو موافقة المالك؛ تُقرأ قائمة `manual` في تقريره وتُستكمل يدويًا. أي قبول حي يحتاج تقريرًا منقحًا مرتبطًا بالـcommit، لا لقطة نصية بلا مصدر.

## 7. الإيقاف والرجوع وحدودهما

تتوقف الترقية عند schema drift، أو جدول ناقص/تعريف غير متوقع، أو فشل ملكية، أو تسريب نص حساس، أو كسر سلسلة الأدلة، أو فشل readiness، أو اختلاف الـcommit. لا retry أعمى ولا حذف بيانات ولا إصلاح ذاتي ولا تفعيل موصل خارجي لحل المشكلة.

- **فشل قبل اكتمال الترحيل:** اقرأ `--status` والتعريف الفعلي، احتفظ بالأدلة، أصلح السبب ثم أعد الترحيل idempotently على البيئة المعزولة. لا تُسقط الجدول الأول لمحاكاة rollback.
- **فشل الكود الجديد بعد ترحيل ناجح:** يمكن تقييم الرجوع إلى صورة سابقة متوافقة؛ الجداول الإضافية تبقى غير مستخدمة من الكود القديم. يلزم فحص صورة الرجوع وإعداداتها فعليًا، ولا يُفترض نجاح ذلك لمجرد أن SQL إضافي.
- **فشل بعد كتابة بيانات:** رجوع الكود ليس restore لقاعدة البيانات. الاستعادة من نسخة مستقلة قرار وإجراء منفصلان، ولا `DROP` تلقائي للجدولين.
- **النشر المُدار:** اتبع `npm run deploy:release -- status` ومسارات `rollback/recover` في [دليل الإصدارات](releases-and-recovery.md) عندما ينطبق على الهدف. Render يستخدم آلية المنصة؛ لا تُنسب إدارة خادم OAuth/Webhook إلى CLI الذي يدير MCP فقط.
