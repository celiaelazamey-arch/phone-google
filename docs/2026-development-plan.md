# خطة تطوير وتحسين سيليا — 2026

**تاريخ المراجعة:** 27 أكتوبر 2026 · **نسخة الوثيقة:** 1.0 · **حالة الخطة:** مقترحة للتنفيذ المرحلي، وليست إعلانًا بنشر الميزات المستقبلية.

**خط الأساس المفحوص:** الإصدار `0.2.0` عند `6f1dbb339d648e1109a3f4ce37aea97abf36c940`، بعد دمج [PR #17](https://github.com/celiaelazamey-arch/phone-google/pull/17). تغييرات إعداد هذه الخطة توثيقية فقط؛ لا تغيير للكود أو الاعتماديات أو SQL أو إعدادات التشغيل أو رقم الإصدار.

## 1. النتيجة المطلوبة والالتزام العملي

نطوّر النظام الموجود، ولا نستبدله لمجرد الحداثة. الأهداف:

1. **استمرارية العمل بين جلسات التطوير:** حفظ الأهداف والقرارات والمهام والأدلة والخطوة التالية داخل المستودع، لا في ذاكرة المحادثة وحدها.
2. **ذاكرة تشغيل دائمة:** استكمال المحادثات والمهام بعد إعادة تشغيل التطبيق، مع موافقة وخصوصية وسياسة احتفاظ واضحة.
3. **منع التعارض قبل النشر:** عقود توافق واختبارات مقارنة مع النسخة السابقة، وترحيلات منفصلة ومراجعة بشرية.
4. **استمرار الخدمات المستقلة عند العطل:** تطوير العزل الحالي إلى تعافٍ وتشغيل قابلين للقياس، دون ادعاء أن عزلًا داخل عملية واحدة يساوي توافرًا عاليًا.
5. **توافق حقيقي مع 2026:** إصدارات مدعومة، MCP حديث بعد اختبارات مطابقة، أمان أدوات AI، أدلة سلسلة توريد، وإتاحة عربية؛ لا ترقية عمياء إلى كلمة `latest`.

> لا يمكن التعهد تقنيًا باستحالة فقد أي شيء أو استحالة أي تعارض. الالتزام هو جعل الحفظ والتوافق والاستعادة بوابات واضحة، والتوقف عند غياب دليلها، وعدم إخفاء أي عمل غير محفوظ أو فحص لم يُنفذ. هذه الخطة لا تحوّل المعاينة المؤقتة إلى قاعدة إنتاج بمجرد كتابتها.

اختبارات المتصفح الموجودة تضم 12 حالة عبر الهاتف والحاسوب، لكن لم تُعد تشغيلها محليًا عند إعداد الخطة. نتائج الجلسة السابقة ليست نتيجة جديدة لهذه الجلسة. لم يُختبر اتصال إنتاجي بـGoogle أو WhatsApp أو Gemini هنا. لم تظهر GitHub Releases منشورة عند الجرد؛ وجود `0.2.0` في المصدر ليس دليلًا على نشر حزمة أو خادم.

المعلومات التشغيلية غير المعروفة: مكان الإنتاج ونطاقه، مخطط قاعدة المستخدم الحقيقي، آلية النسخ الاحتياطي، الحجم والحمل، عميل MCP الذي يستخدمه، الميزانية وسياسة الاحتفاظ. لا يُفترض أنها مطابقة للمعاينة.

## 3. عدم ضياع العمل: مساران منفصلان

### أ. ذاكرة المشروع بين جلسات التطوير — محفوظة في هذه الحزمة

- [تعليمات بدء الجلسة](../AGENTS.md) تُعرّف ترتيب قراءة الحالة والتحقق من الفرع.
- [الحالة الحالية](continuity/STATE.md): ما تحقق، ما لم يتحقق، وما نفعله تاليًا.
- [قائمة العمل](continuity/BACKLOG.md): معرف ثابت لكل مهمة، أولوية وتبعيات ومعيار قبول؛ هي مرجع حالة المهام الوحيد.
- [سجل القرارات](continuity/DECISIONS.md): السبب والأثر وحدود التراجع عن كل قرار.
- [بروتوكول الاستمرارية](continuity/README.md) و[قالب التسليم](continuity/SESSION_TEMPLATE.md): بداية الجلسة ونهايتها والتعافي بعد الانقطاع.
- سجلات جلسات مؤرخة تحت `docs/continuity/sessions/`، دون حذف السجلات السابقة أو نسخ أسرار أو بيانات عملاء إليها.
- Git يحفظ التغييرات، والدفع إلى فرع العمل يحفظ نسخة بعيدة. إن تعذر الدفع يُسجل ذلك صراحةً؛ commit محلي وحده لا يُسمى نسخة بعيدة.
- عند تعارض المحادثة مع المستودع، نفحص الكود وGit وحالة GitHub الحالية. الفرع الذي تعطيه البيئة هو المرجع، وليس اسم فرع في تقرير قديم.

هذا حفظ لسياق العمل القابل للاستئناف، **وليس أرشيفًا حرفيًا مضمونًا لكل محادثة خارج المستودع**. أي متطلب مهم يظهر في المحادثة يُحوّل إلى قرار أو مهمة أو سجل جلسة.

### ب. ذاكرة المستخدم والمحادثات أثناء التشغيل — عمل مستقبلي P0

- تخزين الخيوط والرسائل وحالة المهام في MySQL، لا الاعتماد على DOM أو `sessionStorage` أو ذاكرة Node.
- معرف مستخدم وخيط ثابتان، ترتيب رسائل محفوظ، pagination، وتحقق ملكية على كل قراءة وكتابة واستئناف.
- الكتابة داخل transaction؛ لا تعرض الواجهة «تم الحفظ» قبل تأكيد commit. فشل الحفظ يظهر كفشل، لا نجاح وهمي.
- `clientMessageId` أو مفتاح مماثل فريد لمنع مضاعفة الحفظ عند إعادة المحاولة؛ يختلف عن JSON-RPC request ID.
- checkpoints بإصدار/رقم مراجعة؛ تعارض تبويبين أو عاملين يُرفض أو يُدمج صراحةً، لا كتابة صامتة فوق تقدم أحدث.
- تلخيص اختياري مع إصدار ومراجع للرسائل الأصلية؛ الملخص ليس بديلًا وحيدًا عن الأصل ولا مصدر أوامر موثوقًا.
- التصدير والحذف والاحتفاظ محددة للمستخدم؛ لا تتحول «عدم الضياع» إلى احتفاظ دائم غير مصرح به.
- اختبار قبول حاسم: أغلق المتصفح وأعد تشغيل التطبيق؛ استرجع المحادثة والمهام المؤكدة دون تكرار إجراء خارجي.

## 4. سياسة عدم التعارض مع نظامك

المرجع التفصيلي هو [عقد التوافق](compatibility-contract.md). قواعد التنفيذ:

1. جرد البيئة والمنافذ والـproxy وOAuth callback ومخطط MySQL وعميل MCP قبل تعديل تشغيلي.
2. الإبقاء على Express وMySQL والمسارات والضوابط الحالية؛ لا تحويل إلى إطار آخر أو microservices شاملة دون حاجة مثبتة.
3. تغيير صغير لكل PR، مع تفسير الأثر على المسارات والأدوات والبيانات والأسرار والنشر.
4. الميزات الجديدة اختيارية ومعطلة افتراضيًا عند إدخالها؛ لا تغيير صامت لمعنى متغير موجود.
5. لا حذف جداول أو أعمدة، ولا إعادة تهيئة قاعدة قائمة، ولا `docker compose down -v` ضمن الترقية أو الرجوع.
6. الترحيل بأسلوب expand → backfill → switch → contract، مع نسخة قابلة للاستعادة واختبار القراءة بالنسخة السابقة.
7. بوابة schema الحالية صارمة. **حتى الترحيل الإضافي لا يمر تلقائيًا** إذا كان عقد النسخة السابقة لا يقبله؛ يلزم تصميم إصدار جسر/بوابة ترحيل ومصفوفة توافق قبل التنفيذ.
8. لا تنفيذ أو إعادة إرسال رسالة/موعد بسبب إعادة اتصال أو استعادة جلسة؛ الحالات ذات النتيجة غير المعروفة تُصالح مع المزوّد أو تُراجع بشريًا.
9. staging ببيانات مصطنعة أولًا، ثم موافقة ونشر مراقب، ثم جاهزية ورجوع مثبتان.
10. أي تعارض أو اختبار فاشل أو غياب نسخة بيانات مستعادة يوقف الترقية؛ لا تجاوز للبوابة بتغيير رقم الإصدار أو schema فقط.

## 5. ما الذي يجعل الخطة مواكبة لـ2026؟

### إصدارات التشغيل

بحسب جدول Node الرسمي المثبت في §14، وقت إعداد الخطة:

- Node 24 في Maintenance LTS منذ 20 أكتوبر 2026، وينتهي دعمه المجدول في 30 أبريل 2028. نحافظ عليه كخط تشغيل حالي مختبر.
- Node 22 مدعوم حتى 30 أبريل 2027؛ يبقى مسار توافق حاليًا، مع خطة إيقاف معلنة قبل نهاية الدعم.
- بدء LTS لـNode 26 **مجدول في 28 أكتوبر 2026**؛ لا نسميه LTS فعليًا في 27 أكتوبر. نتحقق من الإعلان، ثم نضيفه كمسار تجريبي، ثم نرقّي بعد اختبارات SDK والحاويات والأداء.
- نراجع تحديثات الأمان دوريًا؛ لا نستخدم `npm audit fix --force` أو نرفع majors تلقائيًا. audit نظيف لا يعني خلو النظام من كل ثغرة؛ تحذيرات الاعتماديات المهجورة تدخل سجل المراجعة أيضًا.

### MCP 2026 دون كسر العملاء الحاليين

ثبت وجود وسم `2026-07-28` في المستودع الرسمي، وقرأنا changelog من commit الوسم نفسه. يتضمن تغييرات جذرية: طلبات stateless وبيانات `_meta` لكل طلب و`server/discover` وإزالة handshake القديم وإضافة `resultType`، وتغييرات في الاشتراكات والـheaders والتخزين المؤقت.

الخطة: محولان واضحان للقديم والجديد، واختبارات fixtures مستقلة، وفحص HTTP وstdio والأخطاء والقدرات وحدود JSON Schema. نبقي المسار القديم وعملاءه عاملين حتى اعتماد الترحيل. لا ندّعي المطابقة بمجرد إضافة تاريخ إلى قائمة الإصدارات.

**ذاكرة التطبيق لا تعتمد على جلسة بروتوكول MCP:** تعرف المحادثة والمهمة بمعرفات تطبيق موثقة ومصرح بها. لا تتعارض الاستمرارية مع كون بروتوكول 2026 stateless. كما أن إعادة طلب نقل مقطوع لا تعني السماح بتكرار أثر خارجي؛ سجل idempotency والمصالحة إلزاميان.

### أمن وذكاء اصطناعي قابلان للقياس

- استخدام OWASP ASVS 5.0.0 كأساس قائمة تحقق، دون ادعاء اعتماد أو تدقيق مكتمل.
- رسائل Gmail وDrive وWhatsApp ومحتوى الأدوات **بيانات غير موثوقة**، لا تعليمات تغيّر السياسة أو تمنح صلاحيات.
- فصل القراءة عن الأفعال الخارجية، وتحقق خادمي من الموافقة والصلاحية ومدخلات الأداة قبل أي اتصال.
- حظر SSRF ووجهات الشبكة غير المصرح بها؛ لا تحميل plugins أو skills أو تنفيذ shell ذاتيًا لمجرد اقتراح نموذج.
- اختبارات عربية مصطنعة لحقن الأوامر وتسرب الأسرار والهلوسة والموافقات والبديل المحلي؛ تقاس الجودة والتكلفة والمهلة لكل مزوّد.
- حدود ميزانية وحجم سياق، ونماذج قابلة للضبط وفق توافر الحساب؛ لا اعتماد اسم نموذج «الأحدث» دون فحص فعلي.
- OpenTelemetry/مقاييس وسجلات منقحة اختيارية؛ لا محتوى رسائل أو مفاتيح في traces أو baggage أو prompt logs.
- WCAG 2.2 AA هدف جديد يجمع الفحص الآلي ولوحة المفاتيح وقارئ الشاشة، وليس شهادة تنتج من axe وحده.

## 6. مراحل التنفيذ المرتبة

التوقيت تقديري بعد معرفة البيئة وتوفير staging. برنامج أولي من **8–10 أسابيع عمل**، يمكن تداخل المسارات المستقلة فقط؛ لا موعد تعاقديًا ولا ترقية مجدولة تلقائيًا. حالات المهام التفصيلية في BACKLOG، لا في نسخ متعارضة من هذه الخطة.

| المرحلة | التوقيت التقديري | التسليم | بوابة الخروج |
|---|---|---|---|
| 0 — تثبيت المرجع والاستمرارية | الجلسة الحالية | الخطة، الحالة، القرارات، عقد التوافق، وقالب التسليم | جلسة مستقلة تستطيع تحديد الحالة والخطوة التالية دون إعادة اكتشاف المشروع |
| 1 — جرد وتحصين قبل التغيير | الأسبوع 1 | ملف بيئة منقح، اختبارات عقد، نسخة بيانات واستعادة تجريبية، تصنيف الأسرار | لا متغير تشغيلي مجهول، ولا ترحيل قبل نجاح restore |
| 2 — ذاكرة دائمة وأفعال قابلة للتعقب | الأسبوعان 2–3 | محادثات وcheckpoints وtool runs وoutbox تجريبي خلف خيار معطل | استئناف بعد restart؛ لا فقد للحفظ المؤكد ولا تكرار أفعال بسبب replay |
| 3 — MCP وAI وأمان 2026 | الأسابيع 3–5 | محول MCP حديث، توافق قديم، تقييم عربي، حدود مزودين وتكلفة | مطابقة مثبتة للنسختين، ومنع الأفعال غير المصرح بها في الاختبارات |
| 4 — مراقبة وجودة وواجهة | الأسابيع 4–6 | MySQL integration CI، اختبارات حمل، metrics، استعادة محادثة وWCAG 2.2 | تقرير أداء وإتاحة وانقطاع على بيئة اختبار موصوفة |
| 5 — نشر إنتاجي وتعافٍ | الأسابيع 6–8 | إدارة إصدار الخدمتين، نسخة/ترقية/رجوع فعلية في staging، تنبيهات ومناوبة | restore وrollback موثقان، موافقة المالك، ومراقبة ما بعد النشر |
| 6 — توافر أعلى وتحسين مستمر | الأسبوعان 9–10 أو لاحقًا | عمليات مستقلة وreplicas/blue-green إن بررها الحمل والميزانية | تجربة فشل process/host وفق البنية المختارة؛ ليس مجرد restart للحاوية |

الأولوية: الاستمرارية والجرد والنسخ أولًا، ثم ذاكرة التطبيق، ثم البروتوكول والذكاء، ثم التوسع. لا يؤجل إصلاح أمني عاجل حتى مرحلته إذا اكتُشف أثناء الجرد.

## 7. اتجاه البنية دون إعادة كتابة

```text
الواجهة الحالية / عميل MCP
          │ HTTPS + مصادقة وصلاحية
          ├─ خادم MCP + محولا legacy / 2026
          ├─ خادم OAuth / WhatsApp Webhook
          │
          ├─ وحدات الاستخدام والسياسة والسياق
          ├─ سجل المهام / idempotency / outbox  [مستقبلي]
          ├─ MySQL دائم + نسخ منفصلة واختبار restore
          └─ مزوّدو Google / WhatsApp / AI بقواطع مستقلة

عامل تنفيذ منفصل ومراقبة خارجية             [عند اعتماد المرحلة]
```

نبدأ **modular monolith** وحدودًا واضحة، ونفصل العامل أو المزوّد الثقيل في عملية مستقلة عند وجود سبب. Redis أو vector database أو Kubernetes أو منصة وكلاء إضافية ليست متطلبات تلقائية؛ إضافة كل خدمة تحتاج تكلفة وفائدة واختبار تعافٍ وقرارًا مسجلًا.

الـoutbox لا يمنح exactly-once لدى مزوّد خارجي لا يدعم ذلك. نضمن تفرد النية محليًا، ثم تتبع حالة المزوّد، ونوقف إعادة المحاولة عند `outcomeUnknown`. تغييرات جدولة أو إرسال قوالب WhatsApp تحتاج اعتماد سياسة وموافقات منفصلة؛ لا بث جماعي تلقائيًا.

| السجل | محتواه المقترح | قيد الأمان/الاستمرارية |

| conversation_threads | المالك، العنوان، تواريخ الإنشاء والتحديث، سياسة الاحتفاظ | فصل الملكية؛ لا مشاركة عابرة للمستخدمين |
| conversation_messages | الخيط، الدور، الترتيب، المحتوى، حالة الحفظ ومعرف العميل | قيد فريد ومنع ازدواج الحفظ، وتشفير وفق تصنيف البيانات |
| task_checkpoints | المهمة، الحالة، رقم المراجعة، مراجع المدخلات والنتائج | optimistic concurrency؛ الاستئناف لا يعيد إجراءً خارجيًا |
| tool_runs / operation_outbox | نية العملية، idempotency key، الموافقة، حالة التسليم ومعرف المزوّد | transaction، حالات unknown ومصالحة، وعدم تخزين bearer tokens |
| schema_migrations / audit_events | الترحيلات والأفعال الإدارية المنقحة | تاريخ قابل للتدقيق؛ لا استخدامه بديلًا عن نسخة البيانات |

المقترح يبدأ بمالك واحد كما هو النظام، ولا يفتح تعدد المستخدمين ضمنيًا. RAG والبحث الدلالي يأتيان بعد قياس فائدة البحث العادي، وبموافقة على إرسال البيانات وسياسة حذف تشمل الفهارس والملخصات والنسخ الاحتياطية وفق نافذة الاحتفاظ.

## 9. الجودة: تعريف اكتمال كل تغيير

لا تُغلق مهمة تنفيذية لمجرد وجود كود. يلزم:

- مطلب ومعيار قبول ومعرف في BACKLOG، مع فصل «مقترح» عن «منفذ» وعن «منشور».
- اختبارات وحدة ومسار وتوافق، وفحص SQL حقيقي إذا مسّت التغيير بيانات.
- اختبار النسخة الجديدة على نسخة بيانات مصطنعة بتركيب مماثل، ثم قراءة/تشغيل N−1 عند ادعاء قابلية الرجوع.
- اختبارات فشل: MySQL، مهلة مزوّد، 429، انتهاء OAuth، تكرار webhook، انقطاع العامل، restart، ونتيجة كتابة غير معروفة.
- فحص أسرار واعتماديات وحاوية، وSBOM/provenance للإصدار المنشور. تثبيت Actions بالـSHA يستمر، وتدرس صور الأساس المثبتة بالـdigest مع تحديث أمني مُراجع.
- الهاتف والحاسوب والمسار الفرعي لـPages، ووضوح أن demo لا يحفظ إنتاجيًا.
- تحديث STATE والمهام والقرار عند تغيره وسجل الجلسة؛ ثم commit ودفع/PR أو توثيق عائق الحفظ البعيد.
- لا يؤخذ نجاح CI من تقرير قديم. المرجع للنتيجة المتغيرة هو commit وتشغيل GitHub الحاليان، والفحوص المتجاوزة تُذكر باسمها.
- تعديل وثائق فقط لا يبرر bump لإصدار التطبيق ولا نشر حاوية أو تغيير قاعدة.

بوابات الاستمرارية وعقود التوافق الموضحة هنا إجراءات مراجعة موثقة الآن؛ **أتمتتها الإضافية ليست منفذة بعد** ومُدرجة كمهمتين CONT-003 وCOMP-002.

## 10. مقاييس القبول التشغيلية المقترحة

هذه أهداف نفاوض عليها ونقيسها بعد الجرد، **ليست نتائج حالية أو SLA معتمدًا**:

| المقياس | الهدف الأولي | دليل القبول |
|---|---|---|
| استئناف جلسة تطوير | الوصول للحالة والخطوة التالية خلال 5 دقائق | تجربة جلسة جديدة اعتمادًا على ملفات الاستمرارية |
| استئناف محادثة | كل رسالة أُكد حفظها ترجع بعد restart للتطبيق مع بقاء MySQL سليمة | اختبار تكامل وترتيب وتفرد وملكية |
| RPO لكارثة البيانات | ≤15 دقيقة مبدئيًا عبر نسخ/PITR مناسبة | استعادة لوقت محدد من نسخة مستقلة؛ يراجع وفق الميزانية |
| RTO لكارثة البيانات | ≤60 دقيقة مبدئيًا على حجم متفق عليه | تمرين restore مؤقت ومسجل، لا تقدير من حجم صغير مجهول |
| جاهزية النواة | هدف 99.9% شهريًا بعد اعتماد HA | قياس خارجي وتعريف واضح للانقطاع والاستثناءات؛ الطبقة النائمة المجانية لا تضمنه |
| أداء API المحلي | p95 ≤500ms هدف تجريبي للطلبات غير المعتمدة على مزوّد خارجي | حمل وموارد وقاعدة بيانات موثقة قبل اعتماد الرقم |
| الأفعال الخارجية | لا تكرار في سيناريوهات replay المختبرة، وunknown مرئي | سجل عمليات ومصالحة؛ لا ادعاء exactly-once عالمي |
| الإتاحة | WCAG 2.2 AA للرحلات الأساسية | آلي + لوحة مفاتيح وقارئ شاشة ومراجعة يدوية |
| كلفة AI | سقف متفق عليه وتنبيه ورفض داخلي عند استنفاده | اختبارات حصص وسجل usage منقح؛ مطابقة تقدير التطبيق لفوترة المزوّد |

النسخ: نحدد الوجهة والتشفير والاحتفاظ والنسخة المنفصلة عن حساب التشغيل وإمكان عدم تعديلها، ونحفظ مفاتيح فكها خارج Git ونختبرها. Git يحفظ الكود لا قاعدة البيانات؛ نسخ قاعدة على نفس القرص وحده ليس تعافيًا من كارثة.

## 11. سياسة الإصدارات والخروج إلى الإنتاج

- `0.2.x` مرشح للتحصين المتوافق بعد الموافقة، دون تغيير وظيفة المستخدم سرًا.
- الإضافات الكبيرة كذاكرة المحادثة وMCP الحديث تحصل على minor مخطط وملاحظات ترحيل؛ لا تُعدل manifests الآن لحجز أرقام.
- أي إزالة لمسار/أداة/سلوك عام تُعلن ككسر مع بديل وهجرة وفترة انتقال؛ لا تختبئ داخل patch.
- ليس هناك موعد تلقائي لـ`1.0`؛ يعتمد على الجرد والخصوصية والنسخ واختبارات التوافق والتعافي والتشغيل الحقيقي.
- سياسة الإصدار: build مرة من commit نظيف → SBOM وفحص → provenance وصورة digest → staging → موافقة → فحص مرشّح → تبديل → فحص فعلي → مراقبة → تثبيت السابقة.
- ترحيل البيانات حدث مستقل مُراجع، لا جزءًا خفيًا من تشغيل التطبيق أو rollback.
- أول نشر مُدار ليس له predecessor مُختلق. `0.1.0` مصدر تاريخي فقط؛ الرجوع بالكود لا يستعيد البيانات.
- Render وPages وMCP وOAuth/Webhook أهداف نشر مختلفة؛ لا يُسمى نجاح أحدها نجاحًا للبقية. ملف Render الحالي ذاكرة/autoDeploy للتجربة، وليس ملف إنتاج دائم؛ نفحص هل يُستخدم فعلًا قبل أي تعديل.

دليل التشغيل الحالي يبقى [releases-and-recovery.md](releases-and-recovery.md)، ولا نستبدل أوامره بخطة مستقبلية غير منفذة.

## 12. المخاطر والقرارات التي تحتاج المالك

| المخاطرة | الإجراء |
|---|---|
| بيئة المستخدم غير معروفة | جرد منقح وأسماء المتغيرات فقط؛ لا كلمات مرور أو توكنات في المحادثة |
| تعارض مخطط قاعدة قديمة | فحص schema ومؤشرات/قيود؛ نسخة مستعادة؛ إصدار جسر قبل تغيير بوابة التوافق |
| فقد ذاكرة المعاينة | لا بيانات حقيقية فيها؛ اختيار MySQL دائم قبل اعتماد حفظ المحادثة |
| تكرار إرسال بعد انقطاع | idempotency + outbox + تحقق مزوّد/مراجعة بشرية، لا retry أعمى |
| تحوّل تقرير قديم إلى حقيقة حالية | وسمه تاريخيًا والإحالة إلى STATE وGit وGitHub؛ لا حذفه |
| بيانات شخصية أو موقع استضافة حساس | سياسة موافقات واحتفاظ وإقامة بيانات ومراجعة قانونية عند لزومها؛ لا ادعاء امتثال تلقائي |
| تكاليف غير متوقعة | ميزانية شهرية قبل AI/HA/نسخ مدفوعة؛ المجاني للتجربة لا يعد بتوافر إنتاجي |
| تعدد إضافات أو اعتماديات بلا حاجة | قرار معماري قبل إضافة خدمة، وتجربة خلف خيار وإمكانية إزالة واضحة |
| غياب ترخيص توزيع رئيسي | قرار المالك قبل إضافة LICENSE؛ `private:false` ليس ترخيصًا لإعادة التوزيع |

مطلوب للجرد فقط: أين يعمل النظام الآن؟ ما الخدمات الفعلية؟ هل توجد بيانات يجب حمايتها؟ ما عميل MCP والأجهزة؟ ما حدود الميزانية والاحتفاظ والتوقف المقبول؟ هذه أسئلة اعتماد التنفيذ، ولا تمنع حفظ الخطة الآن.
